# platform/jobs

后台任务的调度、执行与记录。产品的「自动工作」都从这里走。

## 管什么

- **调度**：登记的 `JobDefinition` 由调度器按 `trigger` 触发——`manual`、`startup`、`interval`、`cron`、`event`。
  `cron` 接受显式 `timezone`；不传时按运行这台机器的时区算，这一点由登记方负责（见下）。
- **执行治理**：并发锁（`concurrencyKey`）、单次超时（`timeoutMs`）、重试策略（`retryPolicy`）、载荷归档。
- **运行记录**：每次运行落 SQLite，可按定义查最近一次与分页历史，按保留期清理（`jobRunRetentionPolicy`）。
- **托管 worker**：长跑型任务的 `ManagedWorkerRuntime`，与一次性 job 分开。
- **出网**：`httpRequest` 是给任务用的 HTTP 客户端，带重试分类（`HttpRetryableError`）。

## 不管什么

- **不判断该不该跑。** 资源是否启用、数据源是否就绪、凭据是否配好，都是产品自己的判断；runner 只执行。
- **不替你决定什么时候登记或撤销。** 一个能力被打开时登记、关闭时撤销，是调用方的责任。
- **不是跨进程队列。** 调度与执行在同一个 Electron 主进程里。
- **不管凭据。** 任务载荷里不该出现密钥；需要凭据时从 `platform/secrets` 取。
- **不定义界面呈现。** `projectJobSchedules` 只把定义和最近一次运行投影成视图，页面怎么显示由产品决定。

## 别人该怎么用它

1. **一个可独立开关的能力 = 一个 `JobDefinition`。** 不要登记一个常驻定义、再在 handler 里过滤掉不该跑的情况——那样「已注册」这个状态就永远为真，界面和现实会对不上。
2. **启用时 `setSchedule`，禁用时 `removeSchedule` 该能力拥有的每一条定义。** 一组全禁用之后，注册表里不该留下任何一条。
3. **界面上显示「在跑没有」，要读 `listSchedules()` 的投影，不要从开关值推断。** 开关是用户意图，注册态是事实。
4. **handler 花请求之前重查启用与就绪。** 调度触发时世界可能已经变了。
5. **不要在 handler 里给自己 reschedule。** 调度由调度器负责，自我重排会和它互相追赶。
6. **`owner` 是归属，不是可见性。** 标 `platform` 不代表「用户不该看见」，标 `product` 也不代表「该出现在资源列表」——要区分这两件事，需要的是另一个字段，而不是拿 `owner` 顶替。

**用错了会怎样**：自建 `setInterval` 承担调度，会得到「窗口关掉就不用跑了」「没有运行记录可查」「没有并发锁」「重启后不知道上次跑到哪」四件事同时缺失；而常驻定义 + handler 过滤，会得到一张看起来一直在跑、实际大部分时间什么都不做的任务表。

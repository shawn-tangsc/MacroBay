# 发布说明正文的格式约束

应用「设置 → 关于」里显示的更新说明，读的是 **GitHub Release 正文**，不是仓库里的 release notes 文件。
解析器在 `platform/updates/contracts/releaseNotes.ts`，只认四种格式：小节标题、段落、项目符号、行内加粗。
所以正文不只是网页上的一段文字，还是一块有上限、会变形的内容。

这一页写给**写这一版正文的人**：发版前先按这里数一遍、过一遍，再贴到 Release 页。

## 正文与仓库全文的关系

- 关于页只显示 Release 正文；`docs/reference/release-notes/<版本>.md` 与 `.zh-CN.md` 是同一版的全文，
  供网页阅读与归档。
- **正文是精简版**：可以比全文短、可以少几条，但事实与数字必须与全文一致，正文里不许出现全文没有的说法。
- 正文里的链接点不开，只会显示成文字。要读者去下载或反馈，靠应用里已有的按钮，别在正文里放地址。
- 已经发布的正文是历史记录，发现规则变了就改规则，不回头改已发的那一版。

## 硬上限：200 个内容单元

解析器的上限在 `releaseNotesLimits`：

- `nodes: 200` —— 内容单元数；
- `textCharacters: 20000` —— 整篇字符数；
- `bodyBytes: 256 * 1024` —— 取正文时的字节上限。

**单元怎么数**：小节标题算 1 个、每个段落算 1 个、**列表里的每一项也各算 1 个**，代码块算 1 个。
项目符号很多的那一节，按条数算，不是按一节算。

**超了不会报错，会静默截断**：正文被切到 200 单元，关于页底下多一行
「正文过长，已显示开头部分；完整内容见更新日志」，后面的内容读者看不到。字符数超 20000 同样标记截断。
0.4.3 的正文是 197 单元、贴线未截断；0.4.4 是 72 单元。贴线过的版本只是没踩到，不是有余量。

**发布前数一遍**，判据是 `truncated: false` 且留出余量：

```bash
npx tsx .scratch/marketing/release-notes-units.mts docs-private/iterations/release-note-<版本>.md
# → {"units":72,"truncated":false,"characters":6656}
```

（那个脚本是按同一口径调 `parseReleaseNotes` 的小工具，不入库；没有它时按上面的数法自己数：
小节标题 + 段落 + 列表项。）

## 会变形的写法

- **中英之间用 `---` 分节**：解析成一段正文「---」，读者看到一根孤零零的横杠。中英之间用标题分，不用分隔线。
- **`1. 2. 3.` 编号列表**：每条物理行各自成段，手动折行的后半句会单独成段。要编号就写进项目符号。
- **表格**：没有表格格式，几行会并成一段，列对不上。
- **图片**：只留说明文字，图本身不显示。
- **引用块 `>`**：只去掉行首的 `>`，当普通段落显示。
- **代码块**：保留为代码块，块内不解释任何标记。适合放命令，不适合放说明。

## 阅读端：固定高度，没有展开

关于页的说明块是**固定高度 + 块内滚动**（`.about-notes-scroller` 上 `max-height: min(360px, 46vh)`），
没有「展开全部」按钮；块内滚到底后继续滚，带动外层页面。

所以开头必须是这一版最重要的变化；安装、兼容与已知限制放在**前 3 块**以内——那是读者一打开、
不滚也看得见的一段。

## 发布前检查

1. 数一遍单元数，确认 `truncated: false`，单元数留余量。
2. 过一遍格式：没有 `---` 分节、没有编号列表、没有表格、没有图片、没有地址链接。
3. 过一遍顺序：第一块是不是这一版最重要的变化，限制类信息是不是都在前 3 块。
4. 在发布记录里写一句：单元数、`truncated` 值、以及「已按应用内展示约束检查」。

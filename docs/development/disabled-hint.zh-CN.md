# 禁用控件与它的原因

被禁用的控件必须**在旁边用看得见的文字**说明为什么，`@platform/ui/components/disabled-hint` 的
`DisabledHint` 负责渲染这句原因并把它关联到控件上。只置灰、不解释，等于告诉读者「这里本来有东西」，
然后拒绝说是什么。

## 它管哪一种——以及它不管哪一种

只覆盖一种处境：**能力存在，但此刻被外部条件挡住。** 通知渠道是样板——它真的在，是系统没放行，
而读者可以自己去改。

它**不**管「这个版本没有」。能力不存在的东西**整块不渲染**：没有行、没有开关、也没有理由。
去解释一个本不该出现在屏幕上的控件为什么不能用，是灰着的占位变成永久物的一条路——而一个永远
点不亮的开关，和一颗没有处理函数的图标按钮是同一件事：它告诉读者「这里有东西」，其实没有。

这个区分在调用点有编译期后果：`wired: false` 的渠道**不许有原因文案**（没有行，写了就是死键）；
`wired: true` 且当前不可用 → **必须有原因，缺了编译不过**。

## props

| 字段 | 类型 | 必填 | 含义 |
| --- | --- | --- | --- |
| `labelKey` | `K extends string` | 是 | 原因的 i18n 键。 |
| `resolveText` | `(key: K) => string` | 是 | 调用方的解析入口；解析为空串时这一层不存在。 |
| `children` | `ReactElement` | 是 | 被禁用的控件。 |

```tsx
<DisabledHint labelKey="notifications.desktopBlockedReason" resolveText={t}>
  <Switch checked={false} disabled />
</DisabledHint>
```

## 组件保证的几条

- **可见文字与 `aria-describedby`，两者都要。** 只关联不显示，鼠标用户看不到；只显示不关联，
  读屏走到控件时听不到原因。只挂 `role="note"` 也一样不够——它宣告了一条没人会导航过去的注记。
- **原因和控件在同一视野里**，同一行内位于控件**左侧**。右侧是控件区，句子放在那里会被挤。
- **一行放不下时，原因换行到控件下方**——仍然紧挨着它，**不回左列**：一旦挪回去，它就变成「在解释
  这一行是什么」，而不是「这个控件为什么开不了」。视觉顺序来自 `flex-direction: row-reverse`，
  DOM 里控件仍在原因之前，所以读屏和 Tab 顺序看到的都是「先控件、后原因」。
- **永不做成悬停提示。** 禁用的控件接不到焦点，挂在它上面的提示只剩鼠标能看。这也是它必须是一个
  组件、而不是临时写法的原因：「禁用控件不能靠悬停解释自己」这条不随组件变。
- **组件不缓存任何判断。** 它收的是键，不是结论。原因是否仍然成立，由调用方每次渲染时算。

## 原因必须重算，不能被记住

读者的路径是：看到「系统没放行通知」→ 去系统设置打开 → 回到应用。**如果回来时那行原因还在，
他会以为设置没生效，然后回去再改一遍。**

所以这一类的原因此前**不能是启动时算一次就固定的值**。窗口重新获得焦点时重算，或跟运行时已有的
变更事件走。**不许为它新加定时器**：一个每几秒重读一次权限的设置页，看起来像软件在一直查看你的
系统设置，而且是**为一个只可能被外部改变的值付持续成本**。判据和「业务里不许自己起 interval」
同一条：平台已有的事件就在平台里接，缺事件才补事件。

一句话：**原因是「现在是否仍然成立」的判断，不是「曾经如此」的记录。**

## 文案

句子说的是读者此刻的**处境**，不是他要做的动作：

- 对：`先选一个助手，才能新建会话`
- 错：`点击不可用`——它在解释按钮为什么变灰，而那是读者已经看见的。

真的还有下一步可做时，那是**另一个控件**，不是一句更长的话。

## 怎么验

1. Tab 到控件：读屏在念出控件的同时念出原因。
2. 不悬停也看得见原因，且与控件同行。
3. 让外部条件变一次（放行权限再回来）：原因消失，不需要刷新页面。
4. `resolveText` 返回空串时，既不出现空段落，也不留下指向不存在元素的 `aria-describedby`。
